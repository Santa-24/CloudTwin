3. STEP 1: LAUNCH PRODUCTION AWS EC2 INSTANCE (CONSOLE SETUP)
================================================================================

1. Log in to the AWS Management Console: https://console.aws.amazon.com
2. In the top-right corner, verify the region is `Asia Pacific (Mumbai) ap-south-1`.
3. In the search bar, type "EC2" and click "EC2".
4. Click "Instances" -> Click the orange "Launch instances" button.

Configure Instance Settings:
- Name: `CloudTwin-Production`
- OS Image (AMI): `Ubuntu Server 22.04 LTS (HVM), SSD Volume Type` (64-bit x86).
- Instance Type: `t3.medium` (2 vCPU, 4 GiB Memory).
  *(Next.js container production builds require ~2.5 GB RAM. If using t3.micro,
   you must enable a 2GB Linux Swapfile as detailed in Section 13).*
- Key pair: Choose `cloudtwin-key` or click "Create new key pair" (RSA, `.pem`).
- Network settings: Click "Edit":
  * VPC: Select `cloudtwin-vpc` (or default VPC).
  * Subnet: Select a Public Subnet (e.g. `cloudtwin-public-subnet-1`).
  * Auto-assign public IP: `Enable`.
  * Security group: Create security group `cloudtwin-ec2-sg`:
    - Rule 1: SSH (Port 22) -> Source: `My IP` (or `0.0.0.0/0`)
    - Rule 2: HTTP (Port 80) -> Source: `0.0.0.0/0`
    - Rule 3: HTTPS (Port 443) -> Source: `0.0.0.0/0`  <-- REQUIRED FOR SSL!
- Storage: `30 GiB gp3` SSD.
- Click "Launch instance". Wait ~60 seconds until status shows `Running`.

4. STEP 2: CONFIGURE RDS POSTGRESQL SECURITY GROUP FOR EC2
================================================================================

Allow the EC2 instance to access the PostgreSQL database:
1. Open the VPC Console -> "Security groups".
2. Select the RDS database security group: `cloudtwin-db-sg`.
3. Click "Inbound rules" tab -> "Edit inbound rules" -> "Add rule":
   - Type: `PostgreSQL` (Port `5432`).
   - Source: Search and select `cloudtwin-ec2-sg`.
   - Description: `Allow CloudTwin EC2 instance ingress to PostgreSQL`.
4. Click "Save rules".

11. STEP 9: REAL-WORLD OBSTACLES FACED & EXACT TROUBLESHOOTING SOLUTIONS
================================================================================

During testing and deployment, several edge cases were identified and resolved.
Reference these proven solutions whenever modifying the platform:

--------------------------------------------------------------------------------
Obstacle 1: Git Merge Conflicts During EC2 Code Pulls
--------------------------------------------------------------------------------
Symptom:
  `error: Your local changes to the following files would be overwritten by merge:`
  `  infrastructure/docker/docker-compose.prod.yml`
  `  infrastructure/docker/nginx.conf`
Cause:
  Local modifications or automated scripts touched configuration files directly on EC2.
Resolution:
  Discard or stash local changes before pulling the clean repository:
  ```bash
  git stash
  git pull origin main
  ```

--------------------------------------------------------------------------------
Obstacle 2: 502 Bad Gateway on Simulation Engine & Timeout Tuning
--------------------------------------------------------------------------------
Symptom:
  Running heavy simulations (e.g., 10x traffic surge or failover calculations)
  returned HTTP `502 Bad Gateway` after exactly 60 seconds.
Cause:
  Nginx default `proxy_read_timeout` is 60 seconds. Complex Monte Carlo
  and bottleneck simulations take longer than 60s, causing Nginx to drop the proxy socket.
Resolution:
  Tuned proxy timeouts to 300 seconds in `infrastructure/docker/nginx.conf`:
  ```nginx
  location /api/ {
      proxy_pass http://backend:8000/api/;
      proxy_set_header Host $host;
      proxy_set_header X-Real-IP $remote_addr;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      proxy_connect_timeout 300s;
      proxy_send_timeout 300s;
      proxy_read_timeout 300s;
  }
  ```

--------------------------------------------------------------------------------
Obstacle 3: Python Adapter NameError & Bottleneck Attribute Bugs
--------------------------------------------------------------------------------
Symptom:
  FastAPI server crashed with 500 error when invoking `/simulations/run` or recommendations.
Cause:
  1. `backend/integrations/simulation_engine/adapter.py` referenced an unbound variable `custom_params`.
  2. `backend/integrations/recommendation_engine/adapter.py` accessed `b.resource_name`
     instead of `b.component_id`.
Resolution:
  1. Safely extracted params: `custom_params = scenario_config.get('custom_params', {})`.
  2. Updated attribute resolution to safely fall back between `component_id` and `resource_id`.

--------------------------------------------------------------------------------
Obstacle 4: Browser Insecure Blob Warnings & Mixed Content
--------------------------------------------------------------------------------
Symptom:
  Browser console reported:
  `The file at 'blob:http://...' was loaded over an insecure connection. This file should be served over HTTPS.`
Cause:
  PDF report generation and canvas export blobs were created under HTTP origin.
Resolution:
  Enforced complete HTTPS via DuckDNS + Certbot TLS 1.3 configuration,
  eliminating mixed-content security blocks.

--------------------------------------------------------------------------------
Obstacle 5: Dashboard Reload Bug (Resetting to Landing Page)
--------------------------------------------------------------------------------
Symptom:
  Pressing `F5` or `Ctrl + R` anywhere in the dashboard or canvas redirected
  the user back to the public landing page, losing the active tab state.
Cause:
  `inStudio` and `activeTab` states in `frontend/src/app/page.tsx` were initialized
  to hardcoded default values (`false`, `'overview'`) without inspecting session storage.
Resolution:
  1. Initialized `inStudio` from `localStorage.getItem('cloudtwin_in_studio')` and token check.
  2. Initialized `activeTab` from `window.location.hash` and `localStorage.getItem('cloudtwin_active_tab')`.
  3. Hash routing updates the URL bar with `#simulator`, `#cost`, `#security`, `#architectures`.
  4. Added explicit `handleReturnToLanding()` so returning to the landing page only occurs
     when the user deliberately clicks "Showcase Landing".

--------------------------------------------------------------------------------
Obstacle 6: Real-Time Auto-Sync Across Canvas & Telemetry Tabs
--------------------------------------------------------------------------------
Symptom:
  Changing node configs, adding resources, or switching currency did not update
  Cost Intelligence, Security Posture, or Recommendations without refreshing the page.
Resolution:
  1. Added a 1.5-second debounced auto-save hook in `ArchitectureCanvas.tsx`
     that tracks modifications and auto-persists updates to the backend.
  2. Added a live toolbar indicator: `🟡 Auto-Syncing...` ➔ `🟢 Live Synced` ➔ `Auto-Sync Active`.
  3. Added `syncTelemetry` in `page.tsx` that re-queries cost estimation, security audits,
     and recommendations concurrently, ensuring all panels stay synchronized live.

12. STEP 10: COMPLETE TEARDOWN & BILLING PROTECTION (STOP VS. DELETE)
================================================================================

To avoid unintended AWS charges when you are done testing, use the appropriate teardown procedure:

--------------------------------------------------------------------------------
PROCEDURE A: TEMPORARILY STOP (PAUSE BILLING, PRESERVE ALL WORK)
--------------------------------------------------------------------------------
1. In EC2 Terminal:
   ```bash
   cd ~/CloudTwin
   docker compose -f infrastructure/docker/docker-compose.prod.yml down
   sudo shutdown -h now
   ```
2. In AWS RDS Console -> Databases -> Select `cloudtwin-rds-postgres` -> Actions -> "Stop".
3. In AWS EC2 Console -> Elastic IPs -> Disassociate and Release Elastic IP
   *(Crucial: AWS charges $0.005/hr for idle Elastic IPs left allocated!)*
4. Cost while stopped: **$0 compute charges** (only pennies for dormant storage).

--------------------------------------------------------------------------------
PROCEDURE B: COMPLETE TEARDOWN / PERMANENT DELETION ($0.00 COST FOREVER)
--------------------------------------------------------------------------------
1. EC2: Select `CloudTwin-Production` -> Instance state -> **Terminate instance**.
   (Automatically terminates server and deletes 30 GB EBS disk).
2. Elastic IP: Select IP -> Actions -> **Disassociate** -> **Release Elastic IP address**.
3. RDS: Select `cloudtwin-rds-postgres` -> Actions -> **Delete**:
   - Uncheck "Create final snapshot".
   - Check "Acknowledge deletion".
   - Uncheck "Retain automated backups".
   - Type `delete me` -> Click Delete.
4. DynamoDB: Select `CloudTwinSimulationEvents` -> Click **Delete** -> Type `confirm` -> Delete.
5. S3 Buckets:
   - For `cloudtwin-architecture-vault-...` and `cloudtwin-reports-vault-...`:
   - Click **Empty** -> Type `permanently delete` -> Empty.
   - Click **Delete** -> Type bucket name -> Delete bucket.
6. VPC Security Groups: Delete `cloudtwin-ec2-sg` and `cloudtwin-db-sg`.

13. PRODUCTION MAINTENANCE & ZERO-DOWNTIME UPDATE COMMANDS
================================================================================

When you push code updates to GitHub `main`, deploy to EC2 with zero hassle:

```bash
# 1. Pull latest code
cd ~/CloudTwin
git stash
git pull origin main

# 2. Rebuild and restart services
docker compose -f infrastructure/docker/docker-compose.prod.yml up -d --build

# 3. View live backend logs
docker compose -f infrastructure/docker/docker-compose.prod.yml logs -f backend

# 4. View live Nginx logs
docker compose -f infrastructure/docker/docker-compose.prod.yml logs -f nginx
```

If building on a low-memory instance (t3.micro or t3.small), allocate a 2GB Linux Swapfile:
```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h
```
